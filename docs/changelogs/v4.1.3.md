# Changelog v4.1.3

All notable changes in this release.

## [4.1.3]

> **One expression that cannot be built no longer has to fail the whole request.** The data provider of the owner can report it
> in the response and answer the others; the service that asked decides to throw or to carry on.

---

## Added

### Isolate the expressions that cannot be built

When a request holds an expression that the owner cannot build (an unknown function, a syntax error, an unknown property with EF
Core...), the whole request fails, and with it every property of the same key and the same level. A rolling deployment shows it:
a new consumer asks for a property that an old owner does not have yet.

The data provider of the owner can now isolate such an expression:

```csharp
services.AddFxMap(cfg => { /* ... */ })
    .AddEntityFrameworkCore(c =>
    {
        c.AddDbContexts(typeof(AppDbContext));
        c.IsolateExpressionErrors();
    })
    .AddMongoDb(c =>
    {
        c.AddCollection(users);
        c.IsolateExpressionErrors();
    });
```

It is a setting of each provider (the EF Core and the MongoDB providers support it). Without it nothing changes: the request fails.

With it, the owner answers the expressions it can build and reports the others in the new `ItemsResponse.Errors`:

| | |
|---|---|
| `ExpressionError(Expression, Message)` | e.g. `Expression 'Orders:summ(Total)' failed to build: Unknown function 'summ'` |
| Reported | **once for each expression**, whatever the number of rows, and also when **no row matches** |
| Value of such an expression | none (`null`) in every row |

The service that asked decides what to do:

- with `ThrowIfException()`: a `DistributedMapException.ExpressionsFailed` that holds **all** the errors (`Errors`, and all the
  messages in `Message`);
- otherwise: a warning in the log for each error, and the properties of these expressions are left alone, while the others are
  mapped.

With HotChocolate the fields of a broken expression are `null`, and `ThrowIfException()` throws, as above.

The errors travel with every transport: in the JSON of NATS, RabbitMQ, Kafka, SQS and Service Bus, and in the gRPC contract
(`ExpressionErrorGrpc`, with nullable `expression` and `message`). A version that does not know them ignores them.

### gRPC

- `GrpcClientsConfigurator.AddGrpcHosts` also takes a list of hosts (`IEnumerable<string>`, or an array), for the hosts read from a
  configuration.

## Fixed

- **RabbitMQ: under load a request failed with `JsonException: '0x01' is an invalid start of a value`** (or `'n' is an invalid JSON
  literal`). The consumer of the replies handed the whole delivery (`BasicDeliverEventArgs`) to the request that was waiting, and the
  request read its body *after* the handler of the consumer had returned. The memory of `ea.Body` belongs to the consumer and is
  reused once the handler returns, so under concurrency the request read the bytes of another message. The body is now copied in the
  handler. A concurrency scenario (200 requests at once, each with its own answer) runs for every transport.

## Changed

- **The README of each NuGet package is Markdown only.** NuGet.org does not render the HTML of the GitHub header, so the page of a
  package showed `<p align="center">` as text. The header is in Markdown, the links and images are absolute, and there is no logo, no
  Discord invitation and no badge for what the NuGet page shows itself. The README of GitHub is unchanged. This takes effect on the
  NuGet page of this version (a README cannot be changed after the package is published).

## Removed

- `FxMap.Expressions.DistributedMapExpression<TModel>` and `FxMap.Expressions.FxMapExpression`: public helpers that parsed an
  expression string into a LINQ lambda. Nothing in FxMap used them. If you did, build the lambda with `ProjectionBuilder<TModel>`.

## Known limits

- **A database error still fails the request.** Only the errors raised when the expression is built are isolated: a LINQ expression
  that EF Core builds but cannot translate into SQL fails when the query runs.
- **MongoDB:** an unknown property is not an error (a missing field is `null` in MongoDB). The syntax errors and the unknown functions are.
- **Service Bus:** the transport tests of this feature run only on the emulator (x64) in CI.

---

## Migration

Nothing to do. If you wrote a **custom transport or pipeline** that builds an `ItemsResponse<DataResponse>` from another one, pass its
`Errors` along (`new ItemsResponse<DataResponse>(items, errors)`); the constructor with only the items still exists. If you wrote a
**data provider** on `QueryHandlerBuilder`, override `BuildProjectionWithErrors` to support the isolation.
