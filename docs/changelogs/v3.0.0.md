# Changelog v3.0.0

All notable changes in this release.

## [3.0.0]

> **Breaking release.** Custom pipeline behaviors no longer compile until the type of `next` is changed, and `SingleFlightBehavior` is removed. See the [Migration Guide](#migration-guide). Nothing else in the public API changed since 2.3.5.

---

## Breaking Changes

### 1. Pipeline behaviors take a named delegate instead of `Func<Task<...>>`

`ISendPipelineBehavior<TDistributedKey>` and `IReceivedPipelineBehavior<TDistributedKey>` now receive the next step as a delegate type from `FxMap.Delegates`:

| Interface | `next` before (2.x) | `next` now (3.0) |
|---|---|---|
| `ISendPipelineBehavior<TDistributedKey>` | `Func<Task<ItemsResponse<DataResponse>>>` | `SendHandlerDelegate` |
| `IReceivedPipelineBehavior<TDistributedKey>` | `Func<Task<ItemsResponse<DataResponse>>>` | `ReceivedHandlerDelegate` |

```csharp
public delegate Task<ItemsResponse<DataResponse>> SendHandlerDelegate();
public delegate Task<ItemsResponse<DataResponse>> ReceivedHandlerDelegate();
```

The shape of the call is unchanged (`await next()` / `next.Invoke()`); only the declared parameter type changes. The send and the received pipelines now have distinct types, so a behavior can no longer be wired into the wrong pipeline by accident.

### 2. `SingleFlightBehavior<TDistributedKey>` and `SingleFlightGroup<TValue>` removed

Both were public. `SingleFlightBehavior` was never registered by default: it only existed for applications that added it themselves (`pipe.OfType(typeof(SingleFlightBehavior<>), ServiceLifetime.Singleton)`), to coalesce concurrent identical requests into one in-flight call. Applications that registered it get a compile error until the registration is removed or replaced (see below).

## Migration Guide

### Custom send / received pipeline behaviors

**Before (2.x):**
```csharp
using FxMap.Abstractions;
using FxMap.Responses;

public sealed class TimingBehavior<TDistributedKey> : ISendPipelineBehavior<TDistributedKey>
    where TDistributedKey : IDistributedKey
{
    public async Task<ItemsResponse<DataResponse>> HandleAsync(RequestContext<TDistributedKey> requestContext,
        Func<Task<ItemsResponse<DataResponse>>> next)
    {
        var started = Stopwatch.GetTimestamp();
        var result = await next.Invoke();
        // ...
        return result;
    }
}
```

**After (3.0):**
```csharp
using FxMap.Abstractions;
using FxMap.Delegates;          // new
using FxMap.Responses;

public sealed class TimingBehavior<TDistributedKey> : ISendPipelineBehavior<TDistributedKey>
    where TDistributedKey : IDistributedKey
{
    public async Task<ItemsResponse<DataResponse>> HandleAsync(RequestContext<TDistributedKey> requestContext,
        SendHandlerDelegate next)   // was Func<Task<ItemsResponse<DataResponse>>>
    {
        var started = Stopwatch.GetTimestamp();
        var result = await next.Invoke();
        // ...
        return result;
    }
}
```

For `IReceivedPipelineBehavior<TDistributedKey>` use `ReceivedHandlerDelegate` the same way.

### If you used `SingleFlightBehavior`

Remove its registration. If you still want concurrent identical requests to share one call, a behavior of your own is enough:

```csharp
public sealed class CoalesceRequestsBehavior<TDistributedKey> : ISendPipelineBehavior<TDistributedKey>
    where TDistributedKey : IDistributedKey
{
    private static readonly ConcurrentDictionary<string, Lazy<Task<ItemsResponse<DataResponse>>>> InFlight = new();

    public async Task<ItemsResponse<DataResponse>> HandleAsync(RequestContext<TDistributedKey> requestContext,
        SendHandlerDelegate next)
    {
        var key = string.Join(',', requestContext.Query.SelectorIds.Order()) + "|" +
                  string.Join(',', requestContext.Query.Expressions.Order());
        var flight = InFlight.GetOrAdd(key, _ => new Lazy<Task<ItemsResponse<DataResponse>>>(() => next.Invoke()));
        try
        {
            return await flight.Value;
        }
        finally
        {
            InFlight.TryRemove(new KeyValuePair<string, Lazy<Task<ItemsResponse<DataResponse>>>>(key, flight));
        }
    }
}
```

Register it like any other send pipeline: `cfg.AddSendPipelines(c => c.OfType(typeof(CoalesceRequestsBehavior<>), ServiceLifetime.Singleton))`. As with the removed behavior, the shared call uses the cancellation token of the first caller, so later callers cannot cancel it independently.

## Other changes since 2.3.5

- READMEs: new header, a performance comparison with AutoMapper `ProjectTo`, corrected API names (`MapFxMapperGrpc`, `EntityConfigureOf<T>`, the HotChocolate/NATS example), documented transport naming and options, and a Documentation column in the package tables.
- The XML documentation of `MapFxMapperGrpc` no longer shows the old method name.

All `FxMap.*` packages are versioned 3.0.0 and must be upgraded together.
