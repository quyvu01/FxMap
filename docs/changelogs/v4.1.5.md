# Changelog v4.1.5

All notable changes in this release.

## [4.1.5]

> **The transports recover from an outage, and the servers can be started again.** Tests that cut the connection between a service and a real broker
> found a RabbitMQ consumer that never worked again, and the servers of the transports could not be started again after the supervisor
> stopped them. Kafka gets the settings of the partitions and of the replication.

---

## Fixed

### RabbitMQ

- **The consumer never worked again after the connection to the broker was lost.** The queue of the replies was declared without a name,
  so the broker chose one. A recovered connection declares the queue again with another name, but the requests kept the old name in
  `ReplyTo`: the owner replied to a queue that no longer existed and every request timed out until the process restarted. The client now
  chooses the name of its reply queue (`fxmap-reply-<guid>`, exclusive, auto-delete), so the recovery declares the same queue. The
  consumer works again about 10 s after the broker is back (the recovery interval of the connection).
- A server whose start failed half way (the consumers it had already created stayed on their channels) no longer ends with two consumers
  of the same queue when it is started again.

### Servers of the transports (NATS, SQS, Kafka)

- **A server could not be started again after it was stopped.** The supervisor stops and starts the servers again with the strategies
  `OneForAll` and `RestForOne`, but `StopAsync` disposed the semaphore of the server (and, for Kafka, its consumer): the next start failed
  with `ObjectDisposedException`. Nothing is disposed that a start needs; Kafka creates its consumer on each start. SQS no longer polls the
  same queue twice after a start that is repeated. The default strategy (`OneForOne`) does not stop a server, so it was not affected.
- **SQS logged a normal shutdown as an error** ("SQS Supervisor shutting down..."); it is information, as for the other transports.

### Supervisor of the servers

- **After the restart of every server (`SupervisionStrategy.OneForAll`), a server that was running was reported as `Stopped`.** The run that
  the restart had cancelled read the token of the new run, took the cancellation for a failure and marked the server as stopped.
- **`RestForOne` restarted the wrong servers.** The servers "after" the failed one were taken in the order of a dictionary, not in the order
  of their registration.

## Added

- **Kafka: `Partitions(n)` and `ReplicationFactor(n)`** in `AddKafka(...)`:

  ```csharp
  cfg.AddKafka(c =>
  {
      c.Host("localhost:9092");
      c.Partitions(6);          // partitions of the request topic of each distributed key (default 1)
      c.ReplicationFactor(3);   // replication factor of the topics FxMap creates (default 1)
  });
  ```

  Both were fixed at 1, which does not fit a cluster of several brokers or several instances of a service (an instance gets whole partitions,
  so a topic needs at least as many partitions as the instances that should work at the same time). The values apply only when FxMap
  **creates** a topic; a topic that exists is not changed. The reply topic of a client is read by one consumer and keeps one partition. The default
  stays 1, so nothing changes unless you set them.
- Tests of the supervisor of the servers (restart with backoff, limit of restarts, circuit breaker, the three strategies, stop) and tests that cut
  the connection between a service and a real broker (NATS, RabbitMQ, SQS): the owner listens again, the consumer fails instead of hanging and works
  again, a request in flight ends within its timeout. For NATS, RabbitMQ, SQS and Kafka: a server that is stopped and started again, a caller that
  cancels, and an owner that is slower than the timeout.

## Known limits

- When a SQS server is stopped and started again at once, the first request can be lost: the long poll that was cancelled may still take a message
  (it comes back after the visibility timeout, after the caller has timed out).
- A consumer channel of RabbitMQ that dies while the connection stays open is not noticed by the supervisor (the start of a RabbitMQ or SQS server
  returns once it is set up).
- Kafka: no outage test yet (the broker advertises its own address, so a proxy cannot cut it).
