# Changelog v4.1.0

All notable changes in this release.

## [4.1.0]

> **Computed keys in profiles.** `Of(...)` accepts an expression over the DTO, the counterpart of a computed entity `Id`
> (`Id(x => x.Mrn + x.Code)` on the owner of the data, `Of(x => x.Mrn + x.Code)` on the caller). Keys are now also read
> before any value is written, which fixes a case where a rule could lose its row.

---

## Added

### Expressions in `Of(...)`

```csharp
// The service that owns the data
public class LabResultConfig : EntityConfigureOf<LabResult>
{
    protected override void Configure()
    {
        Id(x => x.Mrn + x.Code);
        DefaultProperty(x => x.Value);
        UseDistributedKey<LabResultDistributedKey>();
    }
}

// The service that asks for it
public class LabResultResponseProfile : ProfileOf<LabResultResponse>
{
    protected override void Configure() =>
        UseDistributedKey<LabResultDistributedKey>()
            .Of(x => x.Mrn + x.Code)
            .For(x => x.Value)
            .For(x => x.Unit, "Unit");
}
```

- `Of(x => x.UserId)` (a property) behaves exactly as before.
- The value of an expression is read with `ToString()`, so `x.A + x.B` on two numbers adds them instead of joining them.
  Join the text yourself when you mean a concatenation.
- An expression that goes through a null (`Of(x => x.Owner.Code)` with no owner) has no key: the object is left alone.
- `Of` throws `DistributedMapException.InvalidProfileSelector` when the expression does not read the DTO
  (`Of(x => "constant")`), when the profile is created.
- **Order:** a key that reads a property filled by another group (`Of(x => x.ProvinceId + x.Suffix)`, `ProvinceId` filled
  by the user key) is resolved after that group. A property of the **same** group that the key reads
  (`Of(x => x.Id + x.Email)` with `For(x => x.Email, ...)`) is not a dependency: the key exists before the group is fetched.
- HotChocolate reads the key of a rule through the same accessor, so computed keys are meant to work there too (see
  *Known limits*).

## Fixed

- **A rule could lose its row when another rule of the same batch overwrote a property read by its key.**
  `MapResponseData` read each key while it was writing the values of the previous rules, so with
  `Of(x => x.Id).For(x => x.Id, ...)` (or the computed form above) the second rule could look for a key that the first one had
  just rewritten. Every key is now read before any value is written.
- `Of(x => x.Address.Code)` used to register the property **`Code`** of the DTO as the key (the name of the last member).
  It is now a computed key through `Address`.

## Removed

- `IPropertyAccessor.PropertyInfo` and `PropertyAccessor<T,TProp>.PropertyInfo`. A computed key has no property and nothing
  in FxMap read it. Only code that **implements** `IPropertyAccessor` or reads this member is affected:
  delete the member (or keep it as a plain property of your class).

## Things to know about conditional expressions

`For(x => x.Prop, c => c.If(...).Expression(...).Else(...))` is not changed by this release, but its behavior is now
documented, because it decides how you can write a condition:

- **Conditions run concurrently.** The conditions of all the rules in a request are resolved in parallel (one task for each
  mapped property, and the distributed keys are fetched in parallel too), on the `IServiceProvider` the mapper was resolved
  from. FxMap does not serialize them: sequential resolution would make a mapping with many properties wait for each condition
  in turn.
- **They may run more than once per request**, once for each mapped object that uses the rule. Keep them cheap and free of
  side effects; cache anything that is expensive.
- **A scoped `DbContext` must not be used directly in a condition.** Two conditions using the same scoped instance at the same
  time throw `InvalidOperationException` ("A second operation was started on this context instance"). Create what you need
  inside the delegate:

```csharp
.For(x => x.Price, c => c
    .If(async (sp, ct) =>
    {
        var factory = sp.GetRequiredService<IDbContextFactory<AppDbContext>>();
        await using var db = await factory.CreateDbContextAsync(ct);
        return await db.Features.AnyAsync(f => f.Name == "NewPricing" && f.Enabled, ct);
    })
    .Expression("NewPrice")
    .Else("Price"))
```

  (a scope from `IServiceScopeFactory.CreateAsyncScope()` works too; services in that scope do not see the state of the
  scope of the request).
- **HotChocolate:** the condition receives the scope of the **field** being resolved, not the scope of the request. A scoped
  `DbContext` is therefore not shared between fields, but scoped services that your middleware filled for the request
  (current user, tenant) are empty there.

## Known limits

- **Index use:** the filter of a computed id is `Mrn || Code = ANY(...)` in SQL, so an index on `(Mrn, Code)` does not help;
  use an expression index, or store the composed id in a column, on large tables.
- **Ambiguity:** `"MRN0001" + "GLU"` and `"MRN00" + "01GLU"` give the same text. Use a fixed width or a separator.
- **HotChocolate:** the code path reads the key through the accessor of the rule, but there are no HotChocolate tests in the
  repository, so computed keys are not covered end to end there.
- **Performance:** the key snapshot adds one list per level in `MapResponseData`; it has not been benchmarked yet.
