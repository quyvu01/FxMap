# Changelog v5.0.0

All notable changes in this release.

## [5.0.0]

> **Breaking: the indexer `Orders[0 10 asc Date]` and the filter `Orders(Status = 'Done')` are gone, replaced by functions.** Filtering, ordering
> and paging a collection are now the functions `:where`, `:orderBy`, `:offset`, `:limit`, `:first` and `:last`, which chain with each other in any
> order and with projections. The indexer had one sort key, a mandatory direction, negative numbers that only meant "the last item"; the filter had to
> come before the functions, so `Orders:orderBy(Date):where(...)` could not be written.

---

## Breaking changes

### The indexer `[...]` is removed from the expression language

An expression with `[` is rejected when it is parsed, with a message that names the functions to use. The analyzer (`FxMap.Analyzers`) reports it
at compile time (`OFX001`) for the expressions written as string literals in `For(...)`, `Else(...)` and so on.

| Before 5.0 | From 5.0 |
|------------|----------|
| `Orders[asc Date]` | `Orders:orderBy(Date)` |
| `Orders[desc Date]` | `Orders:orderBy(Date desc)` |
| `Orders[0 asc Date]` | `Orders:orderBy(Date):first` |
| `Orders[-1 desc Date]` | `Orders:orderBy(Date desc):last` |
| `Orders[5 asc Date]` | `Orders:orderBy(Date):offset(5):first` |
| `Orders[0 10 asc Date]` | `Orders:orderBy(Date):limit(10)` |
| `Orders[5 10 desc Date]` | `Orders:orderBy(Date desc):offset(5):limit(10)` |
| `Orders(Status = 'Done')[0 asc Date]` | `Orders:where(Status = 'Done'):orderBy(Date):first` |
| `Orders[0 asc Date].{Id, Total}` | `Orders:orderBy(Date):first.{Id, Total}` |

The results are the same (the tests of the data providers ran with both spellings). Two things were different in the indexer and are not kept:
`[-2 ...]` (and any negative number but `-1`) was also "the last item", and a function after `[N asc Date]` with a single item was an error.

### The filter `Collection(condition)` is removed; use `:where(condition)`

An expression with parentheses after a property is rejected when it is parsed, with a message that says to use `:where`; the analyzer reports it at
compile time (`OFX001`). The condition inside is the same as before (operators, `&&`, `||`, `,`, functions such as `Items:count > 5`).

| Before 5.0 | From 5.0 |
|------------|----------|
| `Orders(Status = 'Done')` | `Orders:where(Status = 'Done')` |
| `Orders(Status = 'Done'):sum(Total)` | `Orders:where(Status = 'Done'):sum(Total)` |
| `Orders(Year = 2024, Status = 'Active').Items` | `Orders:where(Year = 2024, Status = 'Active').Items` |
| `Company.Departments(IsActive = true).Employees:count` | `Company.Departments:where(IsActive = true).Employees:count` |
| `Provinces(Name:count > 3).{Id, Name}` | `Provinces:where(Name:count > 3).{Id, Name}` |

`:any(condition)` and `:all(condition)` are not changed. A consequence of the move: a function now belongs to the segment it follows, as for every other
function, so the tree of `Customer.Orders:where(...):groupBy(X).{...}` is `Navigation[Customer, Projection(GroupBy(Where(Orders)))]` (custom visitors of
`FilterNode` are not affected: `FilterNode` stays).

### Removed public API

- `IndexerNode` and `IExpressionNodeVisitor.VisitIndexer` (a custom visitor must drop its `VisitIndexer`). `OrderDirection` stays.
- `ExpressionHelpers` and `ExpressionQueryableData` (a helper of the indexer that nothing in FxMap used).
- The exceptions `DistributedMapException.CollectionFormatNotCorrected`, `CollectionIndexIncorrect` and `CollectionOrderDirectionIncorrect`.

### Text left after an expression is an error

`ExpressionParser.Parse` used to ignore what was left after the expression (`Name )`, `Orders:limit(2) Name`). It now throws
`ExpressionParseException: Unexpected '...' at position N`. An expression that worked only because a part of it was ignored fails now.

## Added

New functions for a collection (`FxMap`, LINQ and MongoDB):

| Function | Syntax | LINQ | MongoDB |
|----------|--------|------|---------|
| orderBy | `:orderBy(Key [asc\|desc], ...)` | `OrderBy` / `ThenBy` | `$sortArray` (MongoDB 5.2+) |
| offset | `:offset(n)` | `Skip(n)` | `$slice` |
| limit | `:limit(n)` | `Take(n)` | `$slice` |
| first | `:first` | `FirstOrDefault()` | `$first` |
| last | `:last` | `LastOrDefault()` | `$last` |

- `orderBy` takes several keys: `Orders:orderBy(CreatedAt, CreatedBy desc)`; `asc` is the default. The next keys order the items that are equal on the previous ones.
- The functions chain with filters, other functions and projections:
  `Orders:where(Status = 'Done'):orderBy(Total desc):offset(5):limit(10).{Id, Total}`, `Orders:orderBy(Date):first.Total`.
- `offset` and `limit` take a whole number, 0 or greater; anything else is an error. `first` and `last` give `null` for an empty collection.
- `first` and `last` do not order: write `orderBy` before them (EF Core rejects `LastOrDefault` on an unordered query).

## Fixed

- **A projection or a property after a function that followed a filter was dropped without an error.** `Orders(Status = 'Done'):orderBy(Total):first.{Id}` (before 5.0)
  returned the whole order. It is parsed now. (A consequence of the error for text left after an expression, above.)

## Known limits

- `orderBy` takes property names only (not functions or navigation).
- A MongoDB server older than 5.2 does not have `$sortArray`: `orderBy` fails there.
- MongoDB names the keys of `orderBy` as written in the expression (the same as `distinct`); a field renamed with `[BsonElement]` is not translated.

## Migration

1. Search your profiles and entity configurations for the old syntax: the indexer `[` (`grep -rnE "\[[-0-9 ]*(asc|desc) " --include=*.cs`) and the
   filter, a property followed by `(` and a condition (`grep -rnE "[A-Za-z]\([A-Za-z.:]+ ?(=|!=|>|<|contains|startswith|endswith)" --include=*.cs`, which also
   finds `:any(` and `:all(` and C# calls: those are fine). The analyzer lists both as errors when you build with 5.0.
2. Replace them with the functions of the tables above.
3. **Services that talk to each other must change together for the expressions that used the indexer or the filter.** An expression is sent as text to the service that
   owns the data and parsed there. An owner on 5.0 rejects `[...]` and `Name(...)`; an owner before 5.0 does not know `:orderBy` or `:where`. A consumer on 5.0 with the new
   expressions needs the owners on 5.0 too. There is no spelling that both versions understand, so deploy the owners and the consumers that use these
   expressions in the same window.
4. If you wrote a visitor of the expression tree (`IExpressionNodeVisitor`), remove `VisitIndexer`; the sorting is a `FunctionNode` of `FunctionType.OrderBy` now.
5. If you used `ExpressionHelpers`, `ExpressionQueryableData` or the three `Collection...` exceptions, copy the code you need; there is no replacement.
